# 部分退款与审批

同一订单支持多次全额或部分退款，每笔都经过人工审批。金额需要大于零、最多两位小数，所有成功退款累计不得超过订单实付金额。这里的退款仍是 SQLite 模拟记录，不涉及真实资金。

## 业务流程

以实付 299 元的订单为例：第一次批准 100 元后，累计已退 100 元，剩余 199 元；第二次批准 50 元后，剩余 149 元。之后申请 150 元会被拒绝，申请 149 元可以继续审批。

1. `get_order` 返回 `paid_amount`、`refunded_amount`、`remaining_amount`。
2. `create_refund_draft` 校验归属和余额，为每份草案生成唯一 `request_id`，不执行退款、不预占余额。
3. `approval_node` 保存审批并通过 `interrupt()` 暂停。员工可批准原金额、调整金额或拒绝。
4. `issue_refund` 在 SQLite `BEGIN IMMEDIATE` 写事务内检查申请编号、订单归属及最新余额，再保存退款。
5. 最终回复使用真实执行结果生成金额与余额。答复审查重试不会再次开放本轮退款草案工具；审查达到上限仍保留已执行的退款回执，并标记人工跟进。

两个待审批申请可能同时使用同一笔余额。因此草案通过不代表一定能执行：若另一笔退款先执行，当前申请超过最新余额，则审批记为 `failed`，本笔不退款，需要核对余额后重新申请。

## 金额和幂等

- `money.py` 用 Decimal 校验输入，退款写入 `amount_cents`，累计与余额比较使用整数分。`amount` 保留为展示兼容字段。
- 不再对 `refunds.order_id` 设置唯一约束；同一订单允许多条退款记录。
- `refunds.request_id` 唯一。同一申请、相同订单/客户/金额重复执行，返回原退款记录；复用编号但修改参数会被拒绝。
- 不同申请即使金额相同，也可以分别执行，仍受累计余额限制。
- 申请编号随工作流状态保存，暂停后重新打开 SQLite 检查点仍能使用同一编号。

## 员工调整金额与审计

工作台提供“本次批准金额”输入框。API：

```http
POST /api/v1/staff/approvals/{approval_id}/decision
X-Staff-Token: <本地员工令牌>
Content-Type: application/json
```

```json
{"approved": true, "staff_id": "staff-demo", "amount": 50}
```

省略 `amount` 使用草案申请金额。拒绝时不要携带金额。零、负数、布尔值、非有限数值、超过两位小数的金额会被拒绝；超过余额的有效金额在执行校验阶段失败。

批准记录的 payload 保留 `requested_amount`、`approved_amount` 和 `request_id`，`amount` 更新为本次批准金额。金额发生变化时另写 `approval_amount_adjusted` 操作日志。执行失败保存失败原因；审批状态与实际退款成功状态需要分别判断，不能仅凭员工点击批准认定退款成功。

客户端提交当前 `approval_id`，避免过期页面恢复另一笔申请。API 对已处理审批返回 409；执行校验失败返回业务状态 `failed`，最终回复说明本轮未退款。

## 旧数据升级

`init_db()` 检测旧退款表缺少新字段时，在原数据库目录生成 `*.before-partial-refunds-*.sqlite` 完整备份，再在事务内重建退款表、迁移记录并检查外键。不删除已有订单或退款；失败会回滚退款表替换。

历史退款编号对应 `legacy:<旧退款编号>`。旧版待审批检查点缺少申请编号时使用兼容编号，避免已经退款的旧订单再次执行同一笔退款。

仅更新政策向量索引：

```powershell
python -m ecommerce_after_sales_agent.seed --index-only
```

此命令不初始化业务数据。程序返回的 `policy_version` 为当前展示政策版本，`indexed_policy_version` 标记召回索引版本；更新索引可同步新政策的召回材料。已有数据请勿运行不带 `--index-only` 的演示初始化命令。

## 验证及边界

运行 `python -m unittest discover -s tests -v`。部分退款测试使用临时数据库、脚本模型和真实工作流节点，覆盖多次退款、金额精度、幂等参数冲突、并发超额、审批调整、余额变化、SQLite 检查点重开、旧表备份与迁移失败回滚等场景；不会请求真实模型或支付服务。

代码级金额校验不代表退货期限、商品品类、客户举证等政策条件已自动通过，仍需工具查询与人工判断。真实模型能否准确理解部分退款请求，需要另外进行授权后的在线评测。

业务库退款、审批记录和 LangGraph 检查点不是跨库原子提交。极端情况下若退款落库后进程异常退出，工作流状态或审批列表可能尚未同步，需要凭申请编号核对后恢复；请求幂等避免同编号重复退款，但不等于已经实现自动故障对账。多进程部署及真实支付还需要进一步的任务协调、支付幂等与对账机制。
